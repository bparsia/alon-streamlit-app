# SPARQL serializer for ALOn responsibility queries — ABANDONED, see conclusion at bottom

**This design is a dead end and should not be picked up as written.** Kept in full (not deleted) so the reasoning isn't re-derived from scratch later. See "Conclusion: abandon this design" at the end of this document for the actual outcome and the redirected thread (DL-safe rules via HermiT).

## Context

Thread #1 from the six open work threads (see `project_six_threads_2026-08` memory) — "more ALOn translations, esp. SPARQL" — has been parked pending the compiler-pipeline staging fix. The user pointed out this gate doesn't actually apply to SPARQL: unlike a TBox-based translation (which would need real analysis of the model before serializing, e.g. building GCIs), SPARQL queries run directly against the *same* OWL ABox/TBox the existing `OWLSerializer` already produces — the model-serialization half of the pipeline needs zero changes. Konclude already supports SPARQL execution (`sparqlfile` mode), so there's a ready-made execution engine, not just a query-language target.

Confirmed by reading the actual code (not assumed), including one significant self-correction below (marked ⚠) after initially describing the wrong mechanism:

- `OWLSerializer` serializes the model (moments/histories as named individuals, `succ`/`same_moment` properties, action/proposition `ClassAssertion`s) completely independently of any query. This is reusable as-is for SPARQL — a SPARQL backend loads the identical `.owl` file.
- Today, each *query* (`pres_1_q`, `outcome_m_h1_q`, etc.) becomes an OWL `SubClassOf(formula, query_id)` axiom via `FormulaToOWL` (`alo_translator/serializers/owl.py`), turning "does formula φ hold at this world" into "is this individual classified under a fresh named class" — then `run_analysis_konclude_layered` (`streamlit_app/utils.py`) runs full realization and filters the result down to the one individual (`m_h1` etc.) actually being asked about, discarding results for every other individual. This SubClassOf-injection approach is what SPARQL needs to *replace*, not reuse.
- ⚠ **Corrected 2026-08-26** — the design originally claimed `FormulaNode.expand()` (`alo_translator/model/formula.py`) is the shared, model-independent expansion mechanism both OWL and a new SPARQL path would reuse. **This is wrong.** Traced the real call path end to end: `.expand()` is called ONLY from `alo_translator/parsers/hierarchical_expander.py` (confirmed via `grep -rl "\.expand("` across `serializers/` and `parsers/` — one hit, that file). `hierarchical_expander.py`/`HierarchicalExpander` is reachable only via `alo_docs/_runner.py`'s separate `evaluate:` YAML key path — NOT the `res_analyse` path that `OWLSerializer`/`DatalogIndexSerializer` actually use for real analysis. This is the same dead-ish code path already investigated once this session (the `named_histories` bug fix in the frontmatter cleanup).
  - **What OWL actually does**: `OWLSerializer._add_query_classes()` (`alo_translator/serializers/owl.py:589`) builds an `ExpanderTransformer` (`alo_translator/parsers/expander_transformer.py`) per-serialization, feeds it each `query.formula_string` (plain text, e.g. `"[1 pres]q"`), and `ExpanderTransformer.transform()` walks the *text* parse tree, overriding `pres`/`sres`/`res`/`dxstit`/`but`/`ness` to expand them into a growing set of **named text axioms** (`self.expander.axioms`, each shaped `"<primitive formula string> => f7"`). This is where the actual responsibility-operator semantics live — and it operates entirely on formula *strings*, re-parsed via Lark, not on `FormulaNode` objects.
  - Those axiom strings are then **re-parsed a second time** and fed through `FormulaToOWL` (a separate transformer, same file), which converts the now-primitive formula (only box/diamond/next/conjunction/disjunction/negation/do_action/free_do_action/prop/top/bottom remain, confirmed via `FormulaToOWL`'s `_must_not_appear` guards on pres/sres/res/etc.) into OWL/XML.
  - **Datalog does NOT share `ExpanderTransformer` either** — confirmed via `alo_translator/serializers/datalog.py`, which builds its own separate `PyDatalogExpanderTransformer` (`alo_translator/parsers/pydatalog_expander_transformer.py`). So the responsibility-operator expansion logic is **already duplicated per-backend** in this codebase (once for OWL, once for Datalog) — there is no single shared "expand once, serialize N ways" stage today, despite what the original design assumed.
  - **Consequence for this design**: a `SparqlExpanderTransformer` (own file, mirroring the existing `ExpanderTransformer`/`PyDatalogExpanderTransformer` naming and per-backend-duplication pattern already established) is the consistent, in-keeping approach — not a deviation from how this codebase works, a continuation of it. `FormulaToSPARQL` (analogous to `FormulaToOWL`) then only needs to handle the *primitive* post-expansion constructs (box/diamond/next/conjunction/disjunction/negation/do_action/prop/top/bottom), fed axiom strings produced by `SparqlExpanderTransformer`, exactly mirroring `OWLSerializer._add_query_classes()`'s two-transformer pipeline shape.
- The closed-world/named-individuals property the user flagged is real and important: every moment/history pair is an explicit named individual (confirmed via `_add_action_assertions`/`_add_proposition_assertions` emitting plain `ClassAssertion(ActionName/PropName, individual)` triples — no anonymous individuals anywhere in this ontology). So "for all successors" (`box`, via `same_moment`) is never open-world universal quantification over an unbounded domain — it's checking a known, enumerable, finite set of same-moment individuals. (See confirmed SPARQL negation findings below for how this actually gets implemented, given both `FILTER NOT EXISTS` and `MINUS` are broken on the available Konclude build.)
- Compared the equivalent already-solved problem in `alo_translator/serializers/datalog.py`. NOTE: Datalog *does* support real recursion via named IDB predicates (e.g. `same_moment(I,J) <= same_moment(I,K) & same_moment(K,J)`, a genuine transitive-closure rule already in this codebase) — that is NOT the constraint at play here. The actual shared constraint between Datalog and SPARQL is: **neither has a direct universal-quantification operator** ("for all X, P(X)" isn't a primitive either language can express directly; both only have existential-style pattern matching plus negation). `box` (universal over same-moment individuals) is the one construct that needs this, and both languages solve it the same way — via double-negation ("no X exists for which NOT P(X)"), which is logically equivalent to universal quantification when the domain is bounded, i.e. a fixed, finite, fully-named set of individuals (true here, confirmed no anonymous individuals anywhere in this ontology).
  - Datalog's specific mechanism: `next(items)` → `succ(I,J) & inner(J)` (simple — `succ` is a `FunctionalObjectProperty`, exactly one successor, so no negation trick needed); `diamond(items)` → `same_moment(I,J) & inner(J)` (plain existential, no negation needed); `box(items)` → double-negation via a **fresh named helper IDB predicate** (`box_violation_N(I) <= same_moment(I,J) & ~inner(J)`, then `box` returns `~box_violation_N(I)`) — using a named predicate here is a Datalog *convenience* (lets the double-negation be defined once and reused/composed cleanly), not a requirement of the double-negation technique itself.
  - SPARQL's equivalent: `FILTER NOT EXISTS { ?j same_moment ?i . FILTER NOT EXISTS { <inner pattern on ?j> } }` — same double-negation idea, but SPARQL has no named/reusable rule mechanism, so each `box` occurrence must be written inline as a nested subquery/filter at its own position in the formula tree rather than factored into a shared named predicate. Formulas here are shallow post-expansion (box/diamond/next don't nest more than a few levels deep), so the resulting nested-filter SPARQL is expected to stay readable — flagging this as the one construct worth double-checking carefully once real queries are generated, not as a blocking problem.

## Goal

Build a `FormulaToSPARQL` transformer (parallel to `FormulaToOWL`) plus a `KoncludeAdapter` SPARQL execution path, so ALOn responsibility queries can be answered by running SPARQL `ASK` queries against the *unmodified* model ontology via Konclude's `sparqlfile` mode, instead of injecting per-query `SubClassOf` axioms and running full realization.

## Empirically confirmed facts about this Konclude build (v0.7.0-1135, Mar 2021), tested 2026-08-26

Ran real queries via `sparqlfile` mode against a real serialized `.owl` file (3.1.mmd) before writing any code, per the standing no-reasoner-hypothesizing rule -- these are measured results, not assumptions:

- Result format confirmed: standard SPARQL 1.1 XML Results Format. `ASK` → `<sparql>...<boolean>true|false</boolean></sparql>`. `SELECT` → `<results><result><binding name="...">...`.
- **`ASK` queries with a join across a non-trivial variable binding gave an incorrect `false`** where the equivalent `SELECT` on the identical WHERE clause correctly returned the expected non-empty result (verified: `succ(m_h1, m1_h1)` and `type(m1_h1, q)` both independently confirmed true via ground `ASK` queries; the joined pattern `ASK { alon:m_h1 alon:succ ?x . ?x a alon:q }` returned `false`; the identical pattern as `SELECT ?x WHERE {...}` correctly returned `?x = m1_h1`). Root cause not investigated further (not needed, since SELECT works and is preferable anyway per the next point) -- but this rules out ASK as a safe query form for this build.
- **`SELECT` works correctly, including for multi-variable joins at real scale** (a full `same_moment` closure query returned all 20 correct pairs for 3.1.mmd, matching the model's structure). This also gives a real design improvement over one-`ASK`-per-(query, eval point): a single `SELECT ?idx WHERE {<pattern>}` can return every individual satisfying a query in one Konclude call, then membership for a specific eval point is checked locally -- mirrors how the OWL/realization path already works (compute broadly once, filter to the index of interest), see `run_analysis_konclude_layered` in `streamlit_app/utils.py`.
- **`FILTER NOT EXISTS` is rejected as a SPARQL syntax error** by this build's underlying parser (Redland/Rasqal, per its own log output) -- confirmed with multiple query shapes (with and without an outer `?i a owl:Thing` pattern, with the `owl:` prefix declared), all rejected identically with `'syntax error'`. FILTER NOT EXISTS is a SPARQL 1.1 addition; this Rasqal version may simply predate/not support it.
- **`MINUS` parses correctly and starts real reasoning, but crashes the Konclude binary with a segfault (exit 139)** partway through query answering (confirmed via the process log showing it progressed through classification and into "Computed first complex query result" before crashing). This is a real, reproducible binary crash on this specific build, not a query-syntax issue.
- **HermiT (`/Users/mbassbp2/Downloads/HermiT/HermiT.jar`) has no SPARQL support at all** -- confirmed via `--help`, it's a pure OWL/DL classification-and-consistency reasoner with no `sparqlfile`-equivalent mode. Not viable as an alternative SPARQL engine.

**Consequence for `box`:** since both of SPARQL's negation mechanisms are broken on this Konclude build, `box` (which requires double-negation, see below) cannot be pushed into a single SPARQL query. Workaround (per user direction): decompose `box(inner)` into two positive-only SELECT queries -- (1) `SELECT ?i ?j WHERE { ?i alon:same_moment ?j }` (confirmed working, gives the full same-moment relation) and (2) `SELECT ?j WHERE {<inner's own SPARQL pattern>}` (the set of individuals satisfying the inner formula) -- then compute `box(inner)` locally in Python: `i` satisfies `box(inner)` iff every `j` with `(i,j)` in the same-moment relation is in inner's satisfying set. This pushes the actual negation/universal-quantification logic out of SPARQL entirely and into plain Python set operations, which is exactly the "closed-world, fully-named, finite individuals" property noted above that makes this safe and correct (no risk of an unnamed individual being wrongly included/excluded).

## Design

### 1a. `SparqlExpanderTransformer` — new file `alo_translator/parsers/sparql_expander_transformer.py`

Mirrors `ExpanderTransformer`/`PyDatalogExpanderTransformer`'s existing per-backend-duplication pattern (see Context correction above) — a Lark transformer over `query.formula_string`, overriding `pres`/`sres`/`res`/`dxstit`/`but`/`ness`/`opposing` to expand them into primitive-formula axiom strings (reuse as much of `ExpanderTransformer`'s actual expansion *logic* as possible by reading it closely and porting the same definitions — the responsibility-operator semantics themselves don't change per backend, only how the final primitive formula gets serialized).

### 1b. `FormulaToSPARQL` transformer — new file `alo_translator/serializers/sparql.py`

A `lark.Transformer` mirroring `FormulaToOWL`'s shape (fed the same kind of post-expansion primitive-formula strings `SparqlExpanderTransformer` produces) but emitting SPARQL graph-pattern fragments (strings) instead of OWL/XML, parameterized by a single "current index" variable threaded through recursively (start at `?idx0`, fresh `?idxN` per `next`/`diamond` nesting level — same fresh-variable approach `datalog.py` already uses via `_fresh_var()`/`_substitute_var()`, reusable pattern, not a new idea).

**Negation is NOT expressible inline** (see confirmed findings above: `FILTER NOT EXISTS` syntax-rejected, `MINUS` segfaults). Any construct requiring negation (`negation` itself, and `box` which is defined via double-negation) cannot be compiled into a single query fragment. Two consequences:
- General `negation(inner)` of an arbitrary subformula: **out of scope for this first version** unless/until a working negation mechanism is found. Confirmed (via `FormulaToOWL`'s `_must_not_appear` guards and reading `formula.py`'s `expand()` methods) that post-expansion formulas are built from a specific pattern (conjunctions/disjunctions of `do_action`/`prop`/`next`/`diamond`/`box`, with negation appearing only in specific structural positions like `_free_do_individual`'s `Opp2<action>` exclusion) — needs a real pass over actual expanded queries (not assumed) to confirm whether general negation ever actually appears outside of `box` and the `Opp2` exclusion pattern; if so, scope may be fully coverable without general negation support at all.
- `box(inner)`: handled by decomposition, not inline SPARQL (see below).

Per-construct mapping (each returns a WHERE-clause fragment referencing its bound index variable, used inside a `SELECT ?idx0 WHERE {...}` query — see step 3 below for why SELECT, not ASK):

| Construct | OWL (existing) | SPARQL (new) |
|---|---|---|
| `prop(p)` | `Class IRI=".../p"` (ClassAssertion check via realization) | `?idx a alon:p .` |
| `do_action(a)` / `free_do_action(a)` | `Class`/`ObjectIntersectionOf` with `Opp2<a>` exclusion | `?idx a alon:a .` for `do_action`; `free_do_action`'s `Opp2<a>` exclusion needs the same negation workaround as `box` (see below) since it's `?idx a alon:a . FILTER NOT EXISTS {...}`-shaped -- confirm whether `free_do_action` actually appears in in-scope queries before assuming this needs solving |
| `conjunction` | `ObjectIntersectionOf` | concatenate patterns (SPARQL AND is juxtaposition) |
| `disjunction` | `ObjectUnionOf` | `{ pattern1 } UNION { pattern2 }` |
| `negation` | `ObjectComplementOf` | NOT SUPPORTED inline (see above) |
| `next(inner)` | `ObjectAllValuesFrom(succ, inner)` | `?idx alon:succ ?idxN . <inner on ?idxN>` (no negation needed — `succ` is functional, confirmed `FunctionalObjectProperty` in the OWL output) |
| `diamond(inner)` | `ObjectSomeValuesFrom(same_moment, inner)` | `?idx alon:same_moment ?idxN . <inner on ?idxN>` |
| `box(inner)` | `ObjectAllValuesFrom(same_moment, inner)` | NOT a single query — see decomposition below |
| `top`/`bottom` | `owl:Thing`/`owl:Nothing` | always-true empty pattern / always-false (query returns no rows) |

`biconditional`/`implication` reduce to conjunction/disjunction/negation combinations exactly as `FormulaToOWL` already does — but since general negation isn't available, need to check (real check, not assumed) whether these actually appear in post-expansion formulas at all before deciding whether this reduction is even reachable code.

**`box(inner)` decomposition** (confirmed workaround, tested 2026-08-26): rather than one query, `box` compiles to two SPARQL SELECT queries plus a local Python set computation:
1. `SELECT ?i ?j WHERE { ?i alon:same_moment ?j }` — the full same-moment relation (confirmed working at real scale: correctly returned all 20 pairs for 3.1.mmd's structure).
2. `SELECT ?j WHERE { <inner's own compiled SPARQL pattern, on variable ?j> }` — the set of individuals satisfying `inner`.
3. In Python: `i` satisfies `box(inner)` iff every `j` such that `(i,j)` is in query 1's result set is also in query 2's result set. This is a plain closed-world set-complement check, safe here specifically because every individual in this ontology is named (confirmed via `_add_action_assertions`/`_add_proposition_assertions`, no anonymous individuals) — there's no risk of missing an unnamed same-moment individual that SPARQL wouldn't have enumerated.

This means `FormulaToSPARQL`'s top-level interface can't be "one query string per formula" for formulas containing `box` — it needs to return either a single query (box-free formulas) or a small composite structure (two queries + a combinator function) for formulas containing `box`. Concretely: have the transformer return a small result object (e.g. a dataclass with `queries: List[str]` and a `combine: Callable[[List[Set[str]]], Set[str]]`) rather than a bare string, so `box`-containing and `box`-free formulas share one interface.

Top-level entry point: given a `Query.expanded_ast`, produce the query/queries needed to compute the full set of individuals satisfying that formula (not bound to one evaluation point) — membership for a specific eval point (e.g. `alon:m_h1`) is then checked locally in Python against that set, exactly like the OWL/realization path already does.

### 2. Konclude SPARQL execution — extend `alo_translator/reasoners/konclude.py`

- Add `ReasoningMode.SPARQL` to the enum in `alo_translator/reasoners/base.py`.
- Add a SPARQL branch in `KoncludeAdapter.run()`: build `[konclude_path, "sparqlfile", "-s", query_file, "-i", ontology_file, "-o", output_file, "-w", threads]` instead of the current `realize`/`classification` command, matching the existing `sparqlfile -s ... -i ... -o ...` usage confirmed via `Konclude --help`.
- New result shape needed: a SPARQL `SELECT` result is a set of variable bindings (individuals satisfying the query), not `Dict[str, Set[str]]` (`individual_types`) like realization produces, and not a boolean (ASK is not used, see confirmed findings above). Add a `bound_individuals: Optional[Set[str]]` field to `ReasoningResult` (additive, doesn't disturb the existing realization path) and populate it by parsing Konclude's SPARQL XML result format — confirmed empirically 2026-08-26: `<results><result><binding name="idx0"><uri>...</uri></binding></result>...</results>`, standard SPARQL 1.1 XML Results Format, one `<result>` per row.

### 3. Analysis entry point — new function in `streamlit_app/utils.py`, e.g. `run_analysis_konclude_sparql_layered`

Mirrors `run_analysis_konclude_layered`'s loop-over-`model.evaluations` shape, but per query: build the OWL ontology once per eval point exactly as today (reused, unchanged), then for each `Query` in `model.queries`, generate its SPARQL query/queries via `FormulaToSPARQL` (one query for box-free formulas, two queries + a local combine step for formulas containing `box` — see step 1), run via the new Konclude SPARQL mode, and check whether the specific eval-point individual (e.g. `alon:m_h1`) is in the resulting satisfying set; collect `query_id` into the overall satisfied set if so. This is at least N SPARQL queries per eval point (one or more per responsibility query, `box`-containing queries need two) rather than 1 realization call — a real trade-off (more Konclude invocations, but each is a plain SELECT rather than injecting axioms + full realization) worth measuring once built, not assumed to be better or worse than realization.

## Answered: general negation is pervasive, not scoped to box/Opp2 — this is a real design problem

Checked empirically 2026-08-26 (ran the actual `ExpanderTransformer` the same way `OWLSerializer._add_query_classes()` does, against all real queries for 3.1.mmd's `m/h1/q` eval point): **19 of 36 generated expansion axioms contain negation**, and the dominant pattern is `~[]Xq` — negation applied directly to a `box`-wrapped subformula (`¬□Xq`, "it's not the case that Xq holds at every same-moment index") used as an ordinary conjunct/disjunct inside larger formulas, e.g. `(do(sd1) & f8 & ~[]Xq) v (...)`. This is genuine, general, freestanding negation of a compound subformula — NOT confined to `box`'s own internal double-negation mechanism or `_free_do_individual`'s `Opp2<action>` exclusion. The original hypothesis (negation might be scoped narrowly enough to avoid entirely) is **false** — negation is central to how `pres`/`sres`/`res`/etc. are actually defined (they all appear to hinge on "is NOT-inevitable", i.e. `~[]X<outcome>`), not an edge case.

**This is a real blocker for the current design**, not a solved problem: the `box`-decomposition workaround (two positive queries + local Python combine) only handles negation *of* a `box`'s own inner formula, computed as part of evaluating `box` itself. It does NOT handle negation *applied to* an already-computed `box` result and then combined with other conjuncts/disjuncts — `~[]Xq` here means "compute the set of individuals satisfying `[]Xq` (itself needing the box-decomposition workaround), then take the complement of that set" as one piece of a larger formula, which needs the SAME kind of decompose-and-combine-in-Python treatment, generalized to arbitrary nesting of negation over arbitrary subformulas — not just the one `box` case. So the actual required architecture is: **every subformula (not just `box`) may need to be evaluated as "the set of individuals satisfying it," with negation, conjunction, and disjunction all implemented as Python set operations (complement/intersection/union) over those sets, composed bottom-up** — SPARQL is used only to compute the leaf-level positive facts (`prop`, `do_action`, `succ`/`same_moment` pair sets), everything else (all boolean structure, all negation) happens in Python, not in the query.

This changes `FormulaToSPARQL` from "produces one query string per formula" to something closer to "produces a small evaluation plan / expression tree over SPARQL-backed leaf sets," which needs a proper design pass of its own (see below) before implementation.

## Conclusion: abandon this design (2026-08-26)

Once the negation finding above was reported (general negation is pervasive — 19/36 axioms for even a simple query, dominated by `~[]Xq`-shaped patterns — not confined to `box` or the `Opp2` exclusion), the user made the actual call: **this design is a non-starter**, for a reason worth stating precisely so it isn't relitigated:

If every boolean connective (conjunction/disjunction/negation) has to be computed in Python as set operations over SPARQL-fetched leaf facts, then SPARQL/Konclude is contributing *nothing* an OWL/DL reasoner is actually for — no TBox inference, no classification, no entailment is being exploited. It reduces to "a funny-looking Datalog" (the user's phrase) implemented with much clumsier tooling (a full OWL file, a reasoner subprocess, XML result parsing) than pyDatalog already provides directly and correctly today. The entire motivation for trying a SPARQL backend — bringing OWL/DL reasoning into the responsibility-analysis pipeline via a second execution engine — would be false advertising if built this way.

**Two live alternatives were named, in order of what's actually worth pursuing next:**
1. A different SPARQL-capable reasoner without Konclude's negation bugs (`FILTER NOT EXISTS` syntax-rejected, `MINUS` segfaults) — not currently scoped, no candidate identified yet. Would need the same rigor as this document: confirm SPARQL support exists, confirm negation actually works via real queries, before any design work.
2. **DL-safe rules via HermiT** — the user's stated preference. This is a *genuinely different* approach, not a variant of the SPARQL idea: DL-safe rules are real OWL reasoning extended with rule-based inference designed exactly for "conjunction/negation-as-failure over named individuals," so this wouldn't hit the same "we're not using the DL reasoner for anything" problem. HermiT (`/Users/mbassbp2/Downloads/HermiT/HermiT.jar`, confirmed present on this machine, confirmed via `--help` to have no SPARQL support at all — irrelevant to this path since DL-safe rules aren't SPARQL) is a second, independent OWL reasoner, which also serves thread #2's "pluggable reasoner backends" goal from `project_six_threads_2026-08` memory. Known caveat, stated directly by the user, not yet re-verified: HermiT reportedly doesn't handle 3.5.mmd (or model characteristics like it) in past experience — this was untested "in a while" as of this conversation and needs fresh verification, not assumed still true or still false.

**Next session starting point, if this thread is picked up again:** scope DL-safe rules on HermiT as its own fresh design effort — do not attempt to reuse or adapt anything from this SPARQL document's per-construct table or transformer design, since none of it applies to a rule-based approach. Start by checking HermiT's actual DL-safe-rules support (its CLI/API, not assumed), and re-verify the 3.5.mmd coverage gap empirically before designing around it either way.
